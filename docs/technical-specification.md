# Техническое задание

## 1. Наименование проекта

**DoIt v0.2: система управления задачами**

## 2. Основание для разработки

Проект выполняется в рамках индивидуального задания на учебную практику по специальности «Программирование».

**Срок выполнения:** 09.06.2026 - 27.06.2026  
**Продолжительность:** 3 недели  
**Формат:** дистанционно

## 3. Цель разработки

Разработать веб-приложение для учета личных и рабочих задач пользователей. Приложение должно позволять пользователю регистрироваться, входить в систему, создавать задачи, редактировать их, удалять, менять статус, искать и фильтровать задачи, просматривать личный кабинет и статистику выполнения.

## 4. Используемые технологии

### Frontend

- HTML;
- CSS;
- JavaScript;
- Django templates.

### Backend

- Python;
- Django;
- стандартная система авторизации Django;
- обычные Django views без отдельного REST API.

### База данных

- PostgreSQL.

### Инфраструктура

- Git;
- GitHub;
- Docker;
- Docker Compose.

## 5. Функциональные требования

Система должна поддерживать:

- регистрацию пользователей;
- вход и выход из системы;
- роли `user` и `admin`;
- личный кабинет пользователя;
- создание задач;
- редактирование задач;
- удаление задач;
- изменение статуса задачи;
- поиск задач по названию и описанию;
- фильтрацию задач по статусу;
- статистику задач;
- журналирование действий пользователей;
- хранение данных в PostgreSQL;
- адаптивный интерфейс.

## 6. Статусы задач

В системе используются статусы:

- `Новая`;
- `В работе`;
- `Выполнена`.

## 7. Frontend-часть

Frontend реализуется через Django templates, HTML, CSS и JavaScript без React, Vue и других frontend-фреймворков.

Интерфейс должен содержать:

- страницу регистрации;
- страницу входа;
- личный кабинет;
- список задач;
- форму создания задачи;
- форму редактирования задачи;
- блок статистики;
- поиск и фильтры.

Личный кабинет должен быть простым и понятным:

- блок профиля пользователя;
- блок статистики;
- список задач;
- элементы управления задачами.

Интерфейс должен корректно работать на компьютере и мобильных устройствах.

## 8. Backend-часть на Django

Backend должен выполнять:

- обработку регистрации;
- обработку входа и выхода;
- работу с пользователями;
- работу с задачами;
- проверку прав доступа;
- расчет статистики;
- запись действий в журнал;
- взаимодействие с PostgreSQL.

Для MVP используется стандартная система пользователей Django. Роль `admin` определяется через стандартные признаки администратора Django, роль `user` используется для обычных зарегистрированных пользователей.

## 9. База данных PostgreSQL

Основные сущности:

### users

Используется стандартная таблица пользователей Django.

Роли:

- `user`;
- `admin`.

### tasks

Поля:

- `id`;
- `user`;
- `title`;
- `description`;
- `status`;
- `due_date`;
- `created_at`;
- `updated_at`.

### action_logs

Поля:

- `id`;
- `user`;
- `action_type`;
- `description`;
- `created_at`.

## 10. Авторизация

Для MVP используется стандартная авторизация Django:

- регистрация через форму;
- вход через форму;
- выход из системы;
- доступ к задачам только после входа;
- пользователь видит только свои задачи;
- администратор может управлять данными через Django admin.

JWT, OAuth и внешние сервисы авторизации на этапе MVP не используются.

## 11. Журналирование действий

Необходимо сохранять действия:

- регистрация;
- вход;
- выход;
- создание задачи;
- редактирование задачи;
- удаление задачи;
- изменение статуса задачи.

Отдельная страница журнала на этапе MVP не обязательна, но записи должны быть доступны через Django admin.

## 12. Docker

Проект должен запускаться через Docker Compose.

Планируемые сервисы:

- `web` - Django-приложение;
- `database` - PostgreSQL.

Команда запуска:

```bash
docker compose up --build
```

Сервер для деплоя на старте не требуется. Docker используется для локального запуска проекта.

## 13. Git-процесс

Так как проект выполняется одним человеком, используется простой процесс:

- `main` - стабильная ветка;
- `feature/*` - новые задачи;
- `fix/*` - исправления ошибок.

Коммиты пишутся на русском языке с понятным префиксом.

Примеры:

```text
docs: добавить стартовую документацию
feat: добавить регистрацию пользователя
feat: добавить модель задач
fix: исправить валидацию входа
docker: добавить локальный запуск через compose
```

В репозиторий нельзя добавлять:

- `.env`;
- пароли;
- токены;
- секретные ключи;
- временные файлы;
- логи;
- локальные настройки IDE;
- дампы базы с реальными данными;
- локальные промты и черновики постановки задачи.

## 15. Критерии готовности

Проект считается готовым, если:

- пользователь может зарегистрироваться;
- пользователь может войти и выйти;
- пользователь видит личный кабинет;
- пользователь может создавать, редактировать и удалять задачи;
- пользователь может менять статус задачи;
- работает поиск и фильтрация;
- отображается статистика;
- действия записываются в журнал;
- данные хранятся в PostgreSQL;
- проект запускается через Docker;
- подготовлена документация для сдачи.
